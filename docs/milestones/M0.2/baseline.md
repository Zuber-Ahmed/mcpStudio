# Reconciled product and engineering baseline

Status: M0.2 review candidate. Decision IDs below are recorded in decisions.md. This document proposes defaults within the authorized reconciliation scope; approval is requested on the completed package.

## Product and support scope

BL01: Deliver the existing five-screen local Studio: Dashboard, Project Setup, Architecture Explorer, MCP Studio, Results & Validation. CLI-first delivery in PRD v1.0 is superseded for this MVP. Retain its scan → classify → plan → approve → generate → validate → review domain pipeline. No new settings/admin/marketplace screen, hosted service, CI product, autonomous merge or deployment is added.

BL02: The core accepts normalized graphs, evidence, capabilities, plans and plugin contracts independent of source language/framework/application domain. Initial analyzer acceptance targets are TypeScript/Node applications using Next.js route handlers and Express/Fastify routes. This is tested plugin coverage, not a restriction embedded in the core. Unknown frameworks/constructs produce explicit unknown/unsupported findings. Python/Java/.NET analyzers and client/both generation are deferred. Plans can recommend server/client/both/none; only supported server+stdio generation is enabled initially. A client/both recommendation remains visible with an unsupported reason; it is never silently converted to server. None is a valid no-integration outcome with no generate action.

BL03: Use at least three controlled source fixtures: one Next.js service, one Express service, one Fastify service. Each includes a read-only candidate, excluded/blocked sensitive action and source-evidence expectations. The sample customer app, PostgreSQL adapters, Claude branding and hardcoded runtime/protocol labels are fixture content, not core product dependencies or compatibility claims.

## Architecture and topology

BL04: Follow the later Studio architecture: Next.js/React/TypeScript web, Go control API, Python analysis workers, PostgreSQL business state, Temporal workflow execution and local S3-compatible object storage. Generator/policy/validator responsibilities remain logical modules; a separate service per module is not required. Redis is deferred because it is not authoritative or required by the identified flow. Do not build a competing Node CLI orchestration engine or local SQLite source of truth. A TypeScript generated-adapter runtime is compatible with this choice and distinct from the Studio control plane.

BL05: All required services run locally; no paid/cloud account or remote model required. Bind published control ports to loopback. Proposed `/v1` on API port 8080 remains a configurable local default, not a running service. Web calls the local control API under a defined origin/auth policy. Bootstrap uses one local operator and one local workspace tenant; no account signup, tenant administration or role-management UI. Keep tenant-scoped keys and server-derived ownership to preserve authorization boundaries without adding an enterprise tenancy feature.

BL06: Windows host with container-backed Linux worker execution is the readiness target. Do not execute arbitrary repository scripts on the Windows host, use an unsafe fallback, or claim support before a local fixture proves bind mounts/path handling, network controls, resource limits and cleanup. Initial scan is read-only; generation writes only into a separate output/worktree. A source snapshot records immutable bytes/digest, including local dirty working content subject to ignore rules. No `.mcp/manifest.json` or other source write occurs just because analysis completes.

BL07: Exact Node/Next.js/Go/Python, container images, MCP protocol/SDK and compatible client versions must be pinned and checked as a single readiness artifact before dependency installation. Historical `2024-11` labels, `npx -y` commands and API SDK examples are not version decisions. Remote HTTP transport is deferred; UI does not offer unsupported transports as executable options. No software-version compatibility claim is made by this baseline.

## Security, consent and retention

BL08: Authentication remains server-side. Local bootstrap creates an opaque random operator credential outside project snapshots and generated bundles; the browser does not persist it in localStorage or expose it in URLs. A bootstrap/session mechanism must specify HttpOnly session handling, CSRF protection for mutations, allowed origins, token rotation and logout before the API is exposed to a browser. Do not ship a static hardcoded bearer token. All resource reads/mutations require current project authorization; local-only is not an authorization bypass.

BL09: Deterministic analysis works offline. Semantic inference is disabled by default; no model adapter call without explicit, scoped consent identifying provider, payload categories, redaction and retention disclosure. The initial deterministic release can show an unavailable semantic option rather than falsely claim an AI recommendation. No zero-retention guarantee is displayed without provider evidence. Secrets use opaque credential references resolved by a host-side secret boundary; no raw token in source JSON, plan hashes, logs or reports. No hidden telemetry.

BL10: Read-only, least-privilege capabilities by default. Every generated tool calls existing authorized domain services and carries user/tenant context; direct DB access is blocked when that would bypass business rules. Write/admin/financial/bulk-export capabilities remain blocked in the initial generator even when discovered. Treat source text, model output and plugin output as untrusted. Validation has no production credentials, outbound network denied by default, bounded CPU/memory/time, permitted commands and read-only source mounts. Missing sandbox prerequisites blocks validation rather than implying pass.

BL11: Retain snapshots/reports/artifacts locally until explicit workspace cleanup; no automatic deletion of audit/approval evidence. Before any real user repository intake, show the storage location and retention policy and provide an operator-documented cleanup procedure. Detailed erasure/backup policies remain production-readiness work, not a privacy guarantee. Fixtures contain no live secrets or personal data. Bind mount and object-cache scope must be covered by the readiness threat model.

## Visual and workflow authority

BL12: Preserve the supplied five-screen composition, navigation and density. Use DESIGN.md frontmatter token values as the canonical initial map (surface `#f8f9ff`, primary `#004ac6`, primary-container `#2563eb`, default radius `0.25rem`, lg `0.5rem`, xl `0.75rem`), because they are machine-readable and broadly match the export. Use its specified Geist/Inter/JetBrains Mono roles with locally packaged licensed assets. No CDN runtime styles/fonts or remote placeholder logos are required for local operation. Prose neutral-palette alternatives and HTML radius overrides are superseded for consistency. This is a token reconciliation, not a new layout.

BL13: For semantic conflicts, use the secure HTML Results state (mandatory skipped checks block approved bundle), not the old PASS screenshot. Dashboard labels derive from actual state, with a defined mapping in the contract amendment. Failed/partial/running states are visible; no timer-based success or decorative compliance/confidence badges. Graph labels and confidence must come from actual evidence. Graph/matrix inspection, fit/zoom and accessible textual alternatives must work on fixture data before UI acceptance.

BL14: Approval binds exact plan/source/config/plugin/generator/policy versions. Every material change creates a new plan revision and clears confirmation. Atomic backend admission verifies current actor and matching approval, independent of checkboxes. Generation success does not imply validation success. Approved bundle export requires the exact artifact-set digest, pinned policy and all mandatory checks passed. A separate developer draft download remains available only to the authorized local operator under explicit draft policy, with a manifest marking it unvalidated and no deploy/merge action.
