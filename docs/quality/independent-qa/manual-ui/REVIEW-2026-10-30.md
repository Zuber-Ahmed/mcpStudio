# Manual browser QA — first runnable Studio slice

Date: 30 October 2026, Asia/Calcutta. Verdict: **HOLD — functional and design defects found**.

Tested the shipped Next.js UI through browser clicks, form entry, search, refresh, keyboard navigation and screenshots. No API requests were scripted to substitute for these manual flows. The main app at `http://127.0.0.1:8080` displayed login but its saved bootstrap was expired/used. QA launched the same existing executable and static build on a separate loopback-only instance, ultimately at `http://localhost:8081`, using the existing application database and a temporary session code. The user's original server was not restarted. An initial session loss occurred while both instances used the same cookie hostname; its cause was not established. QA then used localhost for separate cookie scope, and excludes that ambiguous incident from product defects.

## Reproduced defects

### MAN-01 — P2: Registered projects cannot be reopened

Steps: register a project; return to Dashboard; click its project name/row. Actual: nothing happens; the URL and Dashboard remain unchanged. The row is a plain div without link/button semantics, and Tab from Search does not reach a project action. Expected: a mouse- and keyboard-accessible action opens the selected project's detail/context. The engineer explicitly promised users could reopen projects, and R04/T04 includes keyboard activation of the correct project. A working backend GET endpoint does not satisfy this UI flow.

### MAN-02 — P2: Relative paths accepted as absolute local sources

Steps: Project Setup → Local folder; name `QA Manual 20261030`; Absolute folder path `relative/path`; Register project. Actual: registration succeeds and persists after refresh. Expected: reject relative input with an actionable inline error before storing an invalid immutable source. Metadata-only registration does not need to read the folder to validate absolute syntax. Acquisition safety and path existence were not tested or claimed.

### MAN-03 — P2: Malformed Git source accepted

Steps: Project Setup → Git repository; name `QA Manual Git invalid 20261030`; Repository URL `not-a-url`; Immutable revision `main`; Register project. Actual: project is persisted. Expected: validate supported Git source syntax and enforce or clearly explain immutable revision resolution. `main` is a mutable branch label, despite the field's immutable-revision wording. No remote acquisition occurred. Structural OpenAPI string validation alone cannot establish usable source semantics.

### MAN-04 — P2: Search changes workspace totals and falsely reports an empty registry

Steps: with registered projects, search `qa-no-match-20261030`. Actual: Registered projects and Awaiting analysis both become zero; empty state says “No projects registered” and “Create the first project.” Expected: workspace totals remain authoritative (or explicitly labeled as filtered counts); the list says “No matching projects” and provides a clear/reset-search action. Before creating further fixtures this reproduced with two registered projects. Evidence: `search-empty.png`.

### MAN-05 — P2: Dashboard does not match the approved visual composition

Compared the delivered dashboard with the preserved Stitch dashboard and reconciled M0.2 BL12/BL13 authority. Actual: dark numbered navigation, large added metrics cards and a substantially reorganized registry replace the light sidebar and compact filter/list composition; project action arrows and status filter controls are absent. Missing future statuses can remain unavailable, but layout/navigation/density changes need design reconciliation. This is a design acceptance gap, separate from the truthful not-implemented states. Evidence: `dashboard.png`; reference: `docs/milestones/M0.1/sources/stitch/dashboard/screen.png`.

### MAN-06 — P3: Blank-name error does not identify the invalid field

Steps: enter three spaces as project name and a local absolute path; submit. Actual: request is rejected with “Project request could not be completed.” Expected: trim/validate before submission and tell the user that a nonblank project name is required. Empty-string input correctly triggers the browser's required-field validation; whitespace bypasses that feedback.
